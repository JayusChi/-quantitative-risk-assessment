# 第一阶段实施说明：行业字段标准与数据合同

## 1. 文档定位

本文是《第一部分项目计划书》的第一阶段可执行开发规格。开发者应以本文为阶段范围，以当前仓库中的 `qra_converter`、`db_qra`、`qra_engine` 为代码基线，不另起一套平行工程。

第一阶段解决两个问题：第一部分究竟要识别哪些数据；这些数据以什么结构、状态和证据要求进入后续解析、复核及第二部分计算。第一阶段只建立标准和可执行合同，不开发 OCR、大模型抽取或完整复核界面。

## 2. 阶段目标与出口

阶段目标：建立一套可版本化、机器可读、能被自动测试的数据标准，使字段字典、候选值、证据、质量问题、复核决定和第二部分输入快照使用同一套标识。

阶段出口必须同时满足：

1. 现有完整合成案例能通过新增 JSON Schema 和 `qra_engine.validation.validate_import_contract`；
2. 第二部分动态节点的每个必需输入都能反查到字段字典条目；
3. 17 组、246 项工程指标能从现有指标目录无损导入字段字典；
4. 候选值必须绑定证据或明确标记允许的非文档来源；
5. 缺失、冲突、低置信度、越界、不适用和待复核均有稳定状态码；
6. 合同、字典和规则改变时必须形成新版本，历史版本不可原地改义。

## 3. 当前基线

必须复用的现有能力：

- `src/qra_engine/validation.py`：第二部分输入合同的最终语义校验器；
- `src/qra_engine/dynamic.py`：动态计算节点、依赖和 `required_inputs` 的权威来源；
- `src/qra_engine/model_specs/qra_indicator_catalog_v1.json`：17 组、246 项工程指标目录；
- `src/qra_converter/contracts.py`：`SourceReference`、`FieldLineage`、`ConversionIssue`、`ReviewItem`、`ConversionResult` 等现有转换合同；
- `resources/mappings/`：版本化字段别名、单位和来源优先级配置；
- `tests/fixtures/qra_synthetic_case_v1.json`：完整合成计算案例；
- `tests/fixtures/converter_phase2/expected_business_case.json`：部分数据转换案例。

现有 `validate_import_contract` 仍是第二部分导入的最终权威。新增 JSON Schema 用于结构、类型和枚举的早期检查，不能删除现有跨字段语义校验。

## 4. 范围边界

本阶段包括：

- 字段字典、单位注册表、术语别名、来源等级和错误码；
- QRA 输入、候选字段、证据、质量问题、复核决定和快照清单 Schema；
- 合同加载、版本校验和 JSON Schema 校验入口；
- 第二部分节点—字段依赖矩阵；
- 最小案例、完整案例、非法案例和黄金答案；
- 对现有映射配置增加合同版本引用。

本阶段不包括：

- 文件上传、ZIP 解压、OCR、视觉模型和大模型调用；
- 自动解决多来源冲突；
- 业务复核页面；
- 修改第二部分计算公式、参数或正式发布状态；
- 用默认值补齐未提供的项目事实。

## 6. 合同清单设计

`manifest.json` 至少包含：

```json
{
  "contract_id": "qra.part1-input",
  "version": "1.0.0",
  "status": "TEST_EDITION",
  "released_at": "2026-08-26",
  "compatible_engine_contract": "qra-engine.import/v1",
  "field_dictionary": "field_dictionary.json",
  "schemas": {},
  "files_sha256": {},
  "supersedes": null
}
```

加载器必须校验清单内每个文件的 SHA-256。任务创建时把 `contract_id`、`version` 和清单哈希固化到转换任务；任务执行中发现合同文件已改变时应失败，不得使用变更后的同名合同继续运行。

## 7. 字段字典规范

### 7.1 单条字段结构

`field_dictionary.json` 顶层包含 `dictionary_id`、`version`、`fields`。每个字段至少包含：

| 属性 | 要求 |
| --- | --- |
| `field_id` | 永久稳定的机器标识，如 `pipeline.operating_pressure`；发布后不复用 |
| `target_path` | 快照 JSONPath 风格路径，如 `pipeline.operating_pressure_mpa` |
| `name_zh` | 中文业务名称 |
| `aliases_zh` | 常见同义表头或文字称呼，只作候选召回 |
| `entity_type` | `PROJECT`、`PIPELINE`、`SEGMENT`、`DEFECT`、`WEATHER_CASE`、`POPULATION_CELL` 等 |
| `value_type` | `string`、`number`、`integer`、`boolean`、`date`、`enum`、`object`、`array` |
| `cardinality` | `ONE`、`OPTIONAL_ONE`、`MANY` |
| `source_unit` | 允许的源单位列表；无单位为 `[]` |
| `canonical_unit` | 标准单位；无单位为 `null` |
| `constraints` | 最小值、最大值、正则、枚举或精度要求 |
| `required_level` | `CONTRACT_REQUIRED`、`NODE_REQUIRED`、`OPTIONAL`、`CONDITIONAL` |
| `required_by_nodes` | 使用该字段的第二部分节点 ID |
| `allowed_source_types` | 允许作为事实依据的资料类型 |
| `evidence_policy` | `DOCUMENT_REQUIRED`、`APPROVAL_REQUIRED`、`SYSTEM_DERIVED`、`MANUAL_ALLOWED` |
| `conflict_policy` | 冲突是否阻断、比较容差和允许的来源排序规则 |
| `sensitivity` | `NORMAL`、`SENSITIVE`、`RESTRICTED` |
| `description` | 业务定义及不应混淆的概念 |

### 7.2 必须登记的对象域

首版至少登记以下对象及现有第二部分路径：

- `metadata`：案例编号、项目名称、数据分类、运行配置；
- `assessment`：评价日期、坐标系、泄漏点间距、后果域和准则集；
- `pipeline`：管线编号、长度、外径/壁厚共性、设计/运行压力、运行温度、气体组分；
- `segments[*]`：编号、起止里程、长度、坐标、外径、壁厚、材质、埋深、阀门、检测和关断时间；
- `engineering_indicators`：现有 17 组、246 项指标；
- `frequency_library`、`frequency_correction_model`、`segment_correction_factor`；
- `weather_joint_probability[*]`；
- `population_cells[*]`；
- `ignition_model`；
- `standard_formula_test_parameters`；
- `raw_data_categories` 与 `data_category_manifest`。

`damage_model`、`mock_adapter_output`、`expected_aggregation`、`validation_expectations` 是测试和模型验证内容，必须标记为测试域，不能作为普通客户资料抽取目标。

### 7.3 动态节点依赖矩阵

从 `dynamic_node_catalog()` 生成初始依赖矩阵并人工补充预检中的隐含字段。至少覆盖：

| 节点 | 关键输入 |
| --- | --- |
| `segment_geometry` | 每段 `segment_id/start_km/end_km/length_km` |
| `failure_frequency` | 分机理基准频率、孔径比例及可解析的修正因子 |
| `leak_point_discretization` | 泄漏点间距、每段起止坐标 |
| `aqt3046_source_term` | 压力、温度、管径、壁厚、上下游阀及物性参数 |
| `jet_fire_thresholds` | 燃烧热、辐射分数及上游源项 |
| `gbt34346_annex_c` | 压力、温度、管径、壁厚及该节点预检字段 |
| `adaptive_evidence_qra` | 管段几何；其他证据影响覆盖率和不确定性 |
| `human_qra` | 频率、泄漏点、源项以及人口、气象、点火等预检字段 |
| `risk_matrix` | 自适应结果；完整 QRA 可用时优先采用完整结果 |

生成工具的输出用于发现差异，评审后的 `expected-node-field-matrix.json` 才是阶段黄金文件。第二部分新增节点或修改必需路径时，合同测试必须失败并要求更新字典。

## 8. 候选值与证据合同

### 8.1 候选字段

候选字段是第三、四阶段的中间事实，不是计算快照。`candidate-field.schema.json` 至少包含：

```json
{
  "candidate_id": "CAND-...",
  "field_id": "pipeline.operating_pressure",
  "entity": {"entity_type": "PIPELINE", "entity_key": "PL-001"},
  "raw_value": "运行压力 7.8MPa",
  "parsed_value": 7.8,
  "normalized_value": 7.8,
  "source_unit": "MPa",
  "canonical_unit": "MPa",
  "confidence": 0.98,
  "extraction_method": "STRUCTURED_TABLE",
  "evidence_ids": ["EVD-..."],
  "quality_status": "PASS",
  "review_status": "PENDING",
  "model_or_rule_versions": {}
}
```

约束：`confidence` 位于 `[0,1]`；`evidence_ids` 不得为空，除非字段字典允许 `APPROVAL_REQUIRED`、`SYSTEM_DERIVED` 或 `MANUAL_ALLOWED`；系统派生值必须列出派生规则版本和输入候选 ID。

### 8.2 证据位置

`evidence.schema.json` 使用有类型的位置，不把所有位置压成一个字符串：

- 表格：文件、工作表、表格号、行、列、原单元格文本；
- PDF：文件、页码、边界框 `[x0,y0,x1,y1]` 和页面尺寸；
- DOCX：段落索引、表格/行/列、OOXML 部件；没有可靠分页时不得伪造页码；
- 图片：文件、像素边界框、图像宽高；
- 人工录入：操作者、时间、原因；
- 参数库：库 ID、版本、批准文件引用和适用范围。

所有坐标必须同时保存坐标系说明。页码对用户从 1 开始，内部索引如从 0 开始必须显式转换。

## 9. 状态、问题和复核合同

统一质量状态：

- `PASS`：格式和规则通过；
- `INFO`：存在不改变有效性的转换说明；
- `WARNING`：可进入复核但不可静默忽略；
- `CONFLICT`：多个有效候选不一致，默认阻断；
- `LOW_CONFIDENCE`：低于字段或方法阈值，默认阻断关键字段；
- `MISSING`：没有候选；
- `INVALID`：类型、单位、范围或逻辑错误；
- `NOT_APPLICABLE`：经规则或人工确认不适用。

复核动作只允许：`ACCEPT_CANDIDATE`、`REPLACE_VALUE`、`REJECT_FIELD`、`MARK_NOT_APPLICABLE`、`REQUEST_REEXTRACTION`。每个决定必须有 `review_id`、目标、修改前值、修改后值、复核人、带时区时间、原因和基于的候选/证据 ID。

`issue_catalog.json` 至少预留以下前缀：

- `INTAKE.*`：上传和文件登记；
- `PARSE.*`：文档解析和 OCR；
- `EXTRACT.*`：分类、实体、字段和关系提取；
- `NORMALIZE.*`：单位、桩号、日期、坐标和枚举；
- `FUSION.*`：匹配、重复和冲突；
- `CONTRACT.*`：Schema 和输入合同；
- `GATE.*`：质量门禁；
- `DELIVERY.*`：快照与第二部分联调。

问题码发布后只允许补充，不允许改变既有含义。

## 10. 单位、桩号和术语规则

`unit_registry.json` 每条单位定义符号、量纲、标准单位、精确换算因子、偏移量、允许字段和大小写策略。首版至少覆盖：

- 压力：`Pa`、`kPa`、`MPa`、`bar`，并区分绝压与表压，二者不得仅靠单位自动互换；
- 长度：`mm`、`cm`、`m`、`km`；
- 温度：`°C`、`K`；
- 速度：`m/s`、`km/h`；
- 电位：`V`、`mV`；
- 电阻率：`Ω·m`；
- 频率：首版计算合同只接受 `per_km_year`；
- 比例：小数和百分数，必须由原始百分号或列定义确定，不能按数值大小猜测。

桩号统一输出 `chainage_km` 浮点数，同时保留原文。`K12+300`、`12km+300m`、`12300m` 可确定性转为 `12.3`；缺少基准、单位或存在多种解释时生成阻断问题。

术语别名只生成映射候选，不代表自动确认。例如“工作压力”可以召回运行压力，但当同一资料同时出现设计压力、最高允许操作压力时必须结合列、章节和实体上下文判断。

## 11. QRA 输入 Schema 边界

`qra-input.schema.json` 描述快照的结构和类型，并设置：

- 顶层 `additionalProperties` 采用受控策略：已知计算段严格校验，扩展段必须放在 `extensions`；
- 数值禁止 `NaN`、`Infinity` 和字符串化数字；
- 标准单位体现在字段名或单位属性中；
- 关键数组要求稳定业务主键；
- 快照中不得出现临时候选、提示词全文、模型原始响应或未处理复核项；
- Schema 通过不等于可计算，随后仍调用 `validate_import_contract` 和动态能力规划。

为兼容现有案例，首版 Schema 应允许“部分数据快照”：`metadata`、`pipeline`、非空 `segments` 是导入最低要求；完整 QRA 数据段按节点要求决定可运行性，而非全部设为顶层必填。

## 12. 代码任务拆分

### 12.1 任务 A：生成字段清单

1. 读取现有合成案例、转换黄金案例、动态节点目录和指标目录；
2. 生成初始字段条目，不能手工复制 246 项导致遗漏；
3. 对每个条目标注对象、类型、单位、来源和节点；
4. 人工评审隐含约束，如运行压力不得高于设计压力、管段连续性和概率归一化；
5. 固化字典并生成哈希。

### 12.2 任务 B：编写 Schema 与加载器

1. 编写六个 Schema；
2. `contract_catalog.py` 负责读取清单、验证路径不越界、校验哈希并返回只读元数据；
3. `schema_validation.py` 把 `jsonschema` 错误转换为现有 `ConversionIssue`，路径使用统一表示；
4. 不在加载器内导入数据库或计算引擎；
5. CLI 和 `db_qra` 组合根显式传入合同目录。

### 12.3 任务 C：对接现有映射与任务元数据

1. 映射配置声明合同 ID/版本；
2. 转换结果增加 `contract_id`、`contract_version`、`contract_sha256`；
3. 后续数据库迁移所需字段先在合同中定义，本阶段不强制改造全部 UI；
4. 旧映射配置缺少合同声明时，只允许测试兼容模式并产生 `CONTRACT.LEGACY_PROFILE` 警告。

### 12.4 任务 D：黄金样本和评审

1. 最小案例仅保证导入和 `segment_geometry/adaptive_evidence_qra` 的基础条件；
2. 完整案例来自当前合成案例的受控副本；
3. 非法案例至少覆盖缺段、重复管段、反向桩号、错误单位、概率不归一、证据缺失、未知字段和非有限数；
4. 输出节点—字段矩阵差异报告；
5. 由业务、算法和软件三方确认后将清单状态从 `DRAFT` 改为 `TEST_EDITION`。

## 13. 自动化测试

必须新增并通过：

1. 清单路径、文件哈希和版本一致性测试；
2. 每个 `target_path` 唯一、每个 `field_id` 唯一；
3. 246 项指标全部登记且数量不被硬编码掩盖；
4. 动态节点必需路径全部被字段字典覆盖；
5. 完整合成案例同时通过 JSON Schema 与引擎导入合同；
6. 最小案例只开放预期节点；
7. 候选缺证据、置信度越界、非法复核动作被 Schema 拒绝；
8. 非法数值、概率、单位和桩号产生稳定问题码；
9. 合同文件被修改但版本不变时哈希校验失败；
10. `tools/check_architecture.py` 继续通过。

执行命令：

```powershell
$env:PYTHONPATH = "$PWD\src"
python tools/check_architecture.py
python -m unittest tests.unit.converter.test_contract_catalog -v
python -m unittest tests.unit.converter.test_schema_validation -v
python -m unittest tests.unit.engine.test_validation -v
```

最后执行 `scripts/test.ps1` 全量回归。

## 15. 向第二阶段移交

移交包必须包括合同目录、合同加载方式、允许上传格式清单所需的资料类型枚举、字段敏感级别和问题码。第二阶段只能登记文件和任务，不得绕过本阶段合同直接生成第二部分输入。
