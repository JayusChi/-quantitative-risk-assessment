# 第六阶段实施说明：第二部分联调、端到端测试与验收

## 1. 文档定位

本文是《第一部分项目计划书》的第六阶段可执行开发规格。第六阶段把第五阶段确认的不可变快照提交现有第二部分动态 QRA 引擎，跟踪计算状态、解释错误、支持修订后重算，并用端到端黄金案例完成测试版验收。

第一部分与第二部分当前位于同一模块化单体，但仍必须通过稳定端口联调。适配器不能依赖候选数据、复核页面状态或原始文档，只能读取指定快照。

## 2. 阶段目标与出口

完成“上传资料 → 解析/OCR → 智能提取 → 标准化/融合 → 人工复核 → 不可变快照 → 第二部分计算 → 状态/错误回传”的闭环。正常路径可演示并自动回归；失败路径能定位到字段和证据、回到复核、生成新快照并重算；全过程可追溯。

阶段出口：至少一套完整合成资料包成功驱动第二部分；相同快照、相同引擎/模型配置的数值结果哈希一致；候选或未确认草稿无法被计算；测试参数不会生成正式报告标识；部署、操作、维护和验收记录齐全。

## 3. 当前基线与复用要求

必须复用：

- `src/db_qra/engine_adapter.py` 的 `preview_case()`、`execute_run()`、`calculate_snapshot()`；
- `src/qra_engine/validation.py` 的导入和完整案例校验；
- `src/qra_engine/dynamic.py` 的动态节点规划、隔离执行、能力报告和结果哈希；
- `QraDatabase.create_run/set_run_running/complete_run/fail_run`；
- `calculation_run`、`calculation_node`、结果文档、管段结果和报告资源表；
- `/admin/api/runs`、`/api/runs` 和报告资源接口；
- `tests/fixtures/qra_synthetic_case_v1.json`、现有计算黄金测试和数据库端到端测试；
- `tools/run_stage1_acceptance.py`、`run_stage2_acceptance.py` 等现有验收工具中的可复用模式。

不得为了联调改写已验证计算公式。确需改变数值行为时必须作为第二部分模型变更单独评审、升级版本并更新黄金结果，不得混入第一部分适配器提交。

## 4. 范围边界

本阶段包括：

- 稳定第二部分网关、提交合同、状态和错误映射；
- 计算任务幂等、关联、重试和结果展示；
- 快照—运行—节点—结果—报告完整追溯；
- 端到端案例、故障注入、性能基线和回归；
- 安装、配置、操作、维护和验收文档。

本阶段不包括：

- 用适配器修正快照中的错误字段；
- 把 `PARTIAL` 结果伪装为完整 QRA；
- 在批准参数缺失时开启正式报告；
- 引入微服务、消息队列或分布式事务作为测试版必要条件；
- 真实数据生产验收，后者按总计划 11.7 单独执行。

## 5. 第二部分网关

### 5.1 端口

在 `db_qra` 组合层定义：

```text
Part2Gateway
├─ validate_snapshot(snapshot) -> ValidationResult
├─ plan(snapshot, target_node_ids) -> CapabilityPlan
├─ submit(request) -> SubmissionResult
├─ get_status(external_run_id) -> RunStatus
└─ fetch_result(external_run_id) -> ResultBundle
```

测试版实现 `InProcessPart2Gateway`，内部调用当前 `qra_engine`。端口返回平台 DTO，不把引擎内部异常类、临时目录或 Python 对象泄漏给 HTTP 层。未来远程化时新增 HTTP 网关，不改变上层任务语义。

### 5.2 提交请求

`CalculationSubmission` 至少包含：

- `submission_id` 和幂等键；
- `snapshot_id`、`payload_sha256`；
- `contract_id/version/sha256`；
- `engine_version`、目标节点和图表开关；
- 数据分类、`formal_report_allowed`；
- 发起人、时间和来源门禁运行 ID。

网关从数据库按 `snapshot_id` 加载内容，并再次比对 `payload_sha256`。HTTP 请求不能携带一个同名但不同内容的 `payload` 覆盖快照。

## 6. 合同适配规则

首版快照与第二部分案例结构基本一致，适配器采用“验证后透传”：

1. 验证第五阶段快照清单和内容哈希；
2. 验证合同版本受当前网关支持；
3. 调用 JSON Schema 和 `validate_import_contract`；
4. 检查目标节点在 `plan_dynamic_flow` 中为 `RUNNABLE`；
5. 生成提交请求并加载同一快照内容；
6. 不重命名字段、不填默认值、不单位换算；
7. 任何必要转换必须作为有版本的纯函数适配器，并输出前后哈希和字段级变更清单；首版原则上应为空变更。

适配器支持矩阵写入版本化配置：第一部分合同版本、允许的第二部分导入合同和最低引擎版本。不支持版本返回 `DELIVERY.CONTRACT_VERSION_UNSUPPORTED`，不能尝试猜测兼容。

## 7. 任务与结果状态

### 7.1 传输/执行状态

沿用数据库运行状态：

```text
QUEUED → RUNNING → COMPLETED
             └──→ FAILED
QUEUED/RUNNING → CANCELLED（若实现协作式取消）
```

`COMPLETED` 表示引擎正常结束并固化清单，不等于所有节点均完成。节点与业务结果级别由动态清单表示：

- `PASS`；
- `PARTIAL`；
- `PARTIAL_DATA_ONLY`；
- `BLOCK`。

不得把动态 `PARTIAL` 映射成执行 `FAILED`，也不得在 UI 中显示为“完整 QRA 成功”。

### 7.2 节点状态

完整保留第二部分：`COMPLETED`、`SKIPPED_MISSING_INPUT`、`SKIPPED_DEPENDENCY_FAILED`、`FAILED_ISOLATED`。每个节点保存必需字段缺口、阻断依赖、错误摘要、输出资源和耗时。

### 7.3 重算

- 同一快照可以显式创建多个运行，用于复现或不同目标节点；
- HTTP 提交重试使用客户端幂等键，重复请求返回同一个运行；
- 用户主动点击“重新计算”创建新运行 ID，并记录 `rerun_of`；
- 修订数据必须创建新快照，新的运行记录 `supersedes_run_id` 或业务关联；
- 失败运行不覆盖，所有历史保留。

## 8. 数据库和 API 变更

### 8.1 数据库

为 `calculation_run` 增加或确认：

- `submission_id/idempotency_key`；
- `gateway_id/gateway_version`；
- `contract_id/version/sha256`；
- `target_node_ids_json`；
- `gate_run_id`；
- `rerun_of/supersedes_run_id`；
- `result_tier`；
- `formal_report_allowed`；
- `error_code/error_detail_json`；
- `engine_version`、`input_sha256`、`result_sha256`。

唯一约束只用于幂等请求，不禁止用户显式重算。同一快照的不同运行结果可比较数值哈希。

### 8.2 API

保留并明确：

- `POST /admin/api/runs`：只接受 `snapshot_id`、目标节点、图表开关、幂等键和操作者；
- `GET /admin/api/runs/{run_id}`：运行、节点、结果级别和错误；
- `GET /admin/api/runs/{run_id}/segments`；
- `GET /admin/api/runs/{run_id}/artifacts`；
- `GET /admin/api/runs/{run_id}/export`。

新增：

- `POST /admin/api/runs/{run_id}/rerun`；
- `GET /admin/api/runs/{run_id}/trace`：快照、门禁、合同、引擎和结果哈希链；
- `GET /admin/api/runs/{run_id}/issues`：用户问题和字段路径；
- `POST /admin/api/runs/{run_id}/return-to-review`：基于失败/缺口创建修订任务，不修改原快照。

创建运行前再次检查快照存在、未被篡改、合同支持和目标节点可运行。错误返回 HTTP 400/409，不能先创建运行再因显然缺失失败。

## 9. 错误映射

建立 `delivery_error_catalog.json`，把底层错误转换为稳定、可操作的问题：

| 类别 | 示例 | 用户动作 |
| --- | --- | --- |
| 合同 | 缺字段、类型、版本不支持 | 返回复核并补数/升级合同 |
| 能力 | 目标节点缺输入 | 展示字段、中文名、受影响节点和证据状态 |
| 参数 | 频率库/模型未批准 | 仅允许测试运行或提交批准资料 |
| 数值 | 概率不归一、关系无效 | 定位字段和来源，重新复核 |
| 执行 | 节点隔离失败 | 查看节点错误，可对独立节点继续 |
| 系统 | 存储、线程、资源不足 | 运维重试，不要求用户修改业务值 |

响应和 UI 不显示 Python 堆栈、临时路径或密钥。服务器日志可记录异常链，但必须带运行 ID 并遵守敏感信息规则。

当问题有 `target_path` 时，`return-to-review` 将其映射回字段 ID、候选和证据；无法映射时作为系统/模型问题，不要求用户盲改数据。

## 10. 管理页面联调

运行详情至少显示：

- 快照名称和内容哈希；
- 合同、网关、引擎和模型版本；
- 目标节点与实际节点状态；
- 结果级别：筛查估计或完整人员 QRA；
- PLL、IR、F-N 的可用性分别展示，`null/未计算` 不显示为 0；
- 测试参数/合成数据醒目标识；
- 错误和补数清单；
- “返回复核”“显式重算”“导出结果”和“查看追溯链”。

只有 `formal_report_allowed=true` 且结果合同允许时才显示正式报告入口。测试版报告和导出文件必须带 `TEST_EDITION` 或等价标识。

## 11. 端到端黄金案例

至少建立以下完全合成案例包：

1. `E2E-01-structured-happy`：结构化表格为主，自动映射后少量确认，成功运行筛查节点；
2. `E2E-02-full-qra`：具备频率、坐标、阀门、物性、气象、人口和点火参数，运行完整人员 QRA；
3. `E2E-03-conflict`：设计与检测资料数值冲突，未复核时阻断，复核后新快照成功；
4. `E2E-04-missing`：缺完整 QRA 字段，仅允许批准的部分目标节点；
5. `E2E-05-low-quality-scan`：OCR 低置信度强制人工复核；
6. `E2E-06-malicious-package`：路径穿越/伪装文件在第二阶段阻断，绝不进入计算；
7. `E2E-07-prompt-injection`：文档指令不改变抽取和工具权限；
8. `E2E-08-engine-failure`：故障注入验证错误映射、历史保留和重算；
9. `E2E-09-reproducibility`：相同快照与版本重复计算数值哈希一致；
10. `E2E-10-revision`：修改复核值后产生新快照和新运行，旧链保持可查。

每个案例目录包含原始资料、第三阶段解析黄金、第四阶段候选/问题黄金、复核动作、快照哈希期望、节点状态期望和数值结果/容差。所有资料均为合成，不包含真实资产信息。

## 12. 测试层级

### 12.1 合同测试

- 第一部分 Schema 与第二部分导入校验一致；
- 支持矩阵拒绝未知合同；
- 适配器不改变透传快照；
- 目标节点与能力计划一致；
- 错误码和路径映射稳定。

### 12.2 集成测试

- 快照加载、运行创建、后台执行、节点/结果/资源入库；
- 运行失败、服务重启恢复和幂等提交；
- `return-to-review` 创建新修订任务；
- 报告资源、导出 ZIP 和追溯接口；
- 数据库事务失败不留下半完成结果。

### 12.3 端到端测试

从 HTTP/API 上传原始资料开始，不允许直接跳过第一部分导入黄金 JSON。对慢速外部 OCR/模型使用受控 fixture provider 运行 CI；另有带真实提供方的验收冒烟用例。

### 12.4 数值回归

- 继续运行第二部分全部单元和黄金结果；
- 同快照同版本比较 `numerical_result_sha256`；
- 审计时间和任务 ID 不计入数值哈希；
- 对浮点结果使用现有容差和规范化规则；
- 第一部分改动不得改变既有计算黄金结果。

## 13. 性能和稳定性基线

测试版不承诺生产级吞吐，但必须记录基线：

- 不同格式、页数和文件数的接收/解析/OCR/提取/复核准备耗时；
- 外部调用次数、失败率和重试次数；
- 峰值内存、临时空间和数据库增长；
- 计算节点耗时和报告资源大小；
- 服务重启后的任务恢复时间。

验收资料包的默认目标可设置为：不含外部模型等待时，20 个结构化文件在开发环境内稳定完成；含 OCR/模型的总耗时按提供方单独报告，不以单一总耗时掩盖瓶颈。所有上限写入配置和运维文档。

## 14. 可观测性与审计

结构化日志统一包含 `conversion_job_id`、`review_session_id`、`snapshot_id`、`run_id`、`node_id`（适用时）和问题码。指标至少包含：

- 任务各阶段耗时和失败率；
- 文件类型解析成功率、OCR 低置信比例；
- 字段精确率/召回率、冲突率、人工修订率；
- 门禁阻断原因；
- 运行结果级别和节点失败率；
- 相同快照结果哈希不一致告警。

新增审计事件：`RUN_SUBMITTED_TO_PART2`、`RUN_RERUN_REQUESTED`、`RUN_RETURNED_TO_REVIEW`、`RUN_TRACE_VIEWED`。保留现有 `RUN_QUEUED/STARTED/COMPLETED/FAILED` 和导出事件。

## 19. 测试版完成定义

用户上传一组未经整理的合成项目资料后，系统能够安全登记文件，完成原生解析或 OCR，生成有证据的 QRA 字段候选，识别缺失和冲突；用户在复核工作台作出可审计决定，系统通过目标节点质量门禁并创建不可变快照；第二部分只读取该快照，完成计划内计算并返回可区分的节点状态、风险结果和测试版报告。任一失败都能定位、修订和重算，所有版本、输入、决定和结果哈希可追溯。

达到该定义后，第一部分工程测试版可以验收。真实资料适配、真实准确率校准、安全合规和生产批准仍按《第一部分项目计划书》11.7 执行，不能因测试版闭环而省略。
