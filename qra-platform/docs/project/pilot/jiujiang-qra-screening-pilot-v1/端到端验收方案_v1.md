# 端到端验收方案 v1

## 验收目标

未来验收按以下单向证据链执行：

原始资料 → 文件登记 → 解析/OCR → 候选提取 → 证据绑定 → 冲突复核 → 不可变快照 → 动态计算 → 筛查报告

每一步都可以 `PASS`、`BLOCKED` 或 `FAILED`。被阻断的任务必须保留状态和审计；恢复时创建重试任务或新快照，不覆盖原始证据。

## 逐步验收合同

| 步骤 | 输入 | 执行动作 | 预期输出 | 通过条件 | 阻断条件 | 数据库证据 | 审计事件 | 失败后恢复 |
|---|---|---|---|---|---|---|---|---|
| 1. 原始资料 | 业务方交付的 5～10 份批准源文件 | 数据负责人放入 `workspace/pilots/.../sources/`，核对权限、保密、外发标志和真实/脱敏/合成分类 | 受控源文件集合 | 只在批准目录；`external_sharing_allowed=false`；无真实文件进入 Git 目录 | 路径、权限、责任人或分类未确认 | 尚不入库；以 `source-inventory.csv` 和目录权限为前置证据 | 前置交接记录；正式上传后应产生 `SOURCE_RECEIVED` | 修正保管路径/权限后重新交接；不复制原文件到其他目录 |
| 2. 文件登记 | 受控源文件和脱敏清单 | 逐文件计算字节数、SHA-256、页数/表数、媒体类型和数据日期；解包 ZIP 后逐文件登记 | 唯一 `source_id` 和可复验清单 | source_id 唯一；可用文件有 64 位 SHA-256；数量、大小与实物一致 | 哈希重复未解释、文件名泄密、文件类型不在白名单、ZIP 未解包 | `conversion_job`、`conversion_source`；清单哈希 | `CONVERSION_QUEUED`、`SOURCE_RECEIVED`、必要时 `SOURCE_DUPLICATE_FOUND` / `SOURCE_QUARANTINED` | 修正清单或隔离文件，创建新转换/重试任务；保留原 source 记录 |
| 3. 解析/OCR | 已登记文件、文件类型、受控 OCR 决策 | 表格/原生文档本地解析；仅经安全批准的扫描件进入 OCR；第一版禁止真实云端模型 | 解析产物、页/表结构、警告和失败原因 | 所有文件都有 reader/route；页表数量可对账；解析警告可解释；无未批准外发 | 受保护文件不可读、OCR 未批准、媒体类型伪装、解析结果为空且未解释 | `conversion_parse_artifact`、`conversion_source` 状态 | `CONVERSION_STARTED`、`SOURCE_PARSED` 或 `SOURCE_PARSE_FAILED` | 修复文件或路线后用同一源创建重试任务；失败文件可隔离但不得静默跳过 |
| 4. 候选提取 | 解析产物、v1 字段字典、九江映射 | 按 `jiangxi-natural-gas.jiujiang.v1` 行过滤和列映射；自由文本仅产候选 | 候选字段、实体/关系、标准单位候选、质量问题 | 每个 `field_id` 和 `target_path` 存在于合同；压力、百分比和坐标规则满足；无默认补值 | 未知字段/路径、压力基准不明却映射、缺失写 0、他线记录进入九江范围 | conversion candidates/quality issue 视图；现有管理 API 的候选和质量问题记录 | `EXTRACTION_STEP_COMPLETED`；任务可进入 `CONVERSION_BLOCKED` | 修复专用映射或补资料后重试；合同缺字段时先发布合同版本，不在任务中造字段 |
| 5. 证据绑定 | 每个关键候选及解析定位 | 绑定 source_id、文件哈希、页码/工作表/行列/图片编号和抽取方法 | 可追溯证据对象和候选—证据关系 | 5 个第一版关键字段均有精确位置；关键候选证据数量大于 0；哈希匹配 | 只有文件级来源无页/单元格位置、证据哈希不一致、图片无空间参照却支持坐标 | conversion candidate detail、parse artifact、source 记录；未来/现有候选证据存储 | `EXTRACTION_STEP_COMPLETED`，证据缺失时 `CONVERSION_BLOCKED` | 回到解析/候选步骤补位置；不得人工直接改快照绕过证据 |
| 6. 冲突复核 | 候选、证据、质量问题和冲突集合 | QRA/业务复核人逐项接受、拒绝、请求补证；不按来源优先级自动确认 | 复核决定、理由、复核人、时间和剩余阻断项 | 冲突敏感字段 `review_required=true`；所有阻断冲突有决定；决定可追溯 | 未任命复核人、来源冲突自动确认、坐标/压力/百分比歧义未解决 | conversion review summary、candidate 状态、`review_audit_json` | `CONVERSION_READY` 或 `CONVERSION_BLOCKED` | 补证后创建重试/新复核决定；不删除原决定；错误复核以新决定纠正 |
| 7. 不可变快照 | 已通过复核的业务 JSON、来源清单和决定 | 用户确认转换并写入快照；计算 payload 和来源元数据哈希 | 唯一不可变 `input_snapshot` | 由本试点 conversion 确认产生；payload SHA-256 稳定；包含 1 个签批管段；无虚假默认 | 直接导入旧快照、来源未接管、关键字段无证据、P0 未关闭 | `input_snapshot`、`input_snapshot_provenance`、`input_segment`、`input_indicator_observation`、`input_population_receptor`、`input_raw_record` | `CONVERSION_CONFIRMED`（或受控导入时 `SNAPSHOT_IMPORTED`，但本试点不接受直接导入作为成功路径） | 任何数据变更都创建新 conversion 和新 snapshot；不得修改原快照 |
| 8. 动态计算 | 经确认快照、5 个 `target_node_ids` | 创建 run，按依赖执行节点，保存节点 JSON、管段结果和报告资源 | 5 个目标节点记录、数值哈希、能力报告 | `data_inventory`、`indicator_coverage`、`segment_geometry`、`adaptive_evidence_qra`、`risk_matrix` 完成；0 目标节点失败；层级为筛查 | 目标节点必需输入无来源/gap、节点失败、结果层级越权、使用不同快照 | `calculation_run`、`calculation_node`、`calculation_result_document`、`calculation_segment_result`、`calculation_artifact` | `RUN_QUEUED`、`RUN_STARTED`、`RUN_COMPLETED` 或 `RUN_FAILED` | 修复代码/配置后对同一不可变快照创建新 run；数据变化则先创建新快照 |
| 9. 筛查报告 | 已完成 run、节点结果和能力说明 | 生成 HTML、SVG、JSON、CSV；检查标题、层级、缺口、单段限制和哈希 | 证据条件化定量筛查交付包 | HTML/SVG 可打开；结果层级正确；明确“非完整 QRA/非接受性结论”；1 段排名限制可见；文件哈希入清单 | 报告声称完整/正式 QRA、IR/F-N 缺失被写 0、缺口或不确定性声明缺失、文件损坏 | `calculation_artifact` 和 run summary；导出清单 | `RESULT_EXPORTED` | 仅修复渲染时可基于同一 run 重新导出并保留版本；数值变化必须新 run |

## 验收查询要点

验收人员至少核对：

1. `conversion_source` 数量、字节数和哈希与脱敏清单一致；
2. 关键候选的 `field_id`、`target_path`、单位和证据位置与 `field-node-matrix.csv` 一致；
3. conversion 事件顺序包含收到源文件、开始转换、解析、就绪/阻断和确认；
4. `input_snapshot_provenance` 指向本试点 conversion，而不是历史直接导入快照；
5. `calculation_node` 仅要求 5 个目标节点成功，非目标完整 QRA 节点可因显式缺口跳过；
6. `calculation_segment_result` 只有 1 个权威管段，且报告不把第 1 名解释为局部高风险位置；
7. 报告资源和输入/数值结果哈希可重复，所有外发标志为 false。

## 自动化与人工验收分工

- `tools/validate_pilot_scope.py` 在运行前检查 manifest、字段/节点/来源引用、必需输入闭环、证据与复核策略、默认值、报告层级和真实资料目录污染；
- 转换与计算自动测试保证实现不回归；
- 数据负责人确认文件真实性、保密和时间范围；
- 业务负责人确认管线与权威管段；
- QRA 复核人确认字段解释、冲突、参数和报告边界；
- 只有机器校验为 `READY` 且三方签批完成，才能执行真实试点验收；当前三个虚拟角色只授权内部测试，正式发布仍须真实责任人重新签批。

## 当前预验收结论

定义包机器校验结果为 `validation_status=PASS`、`status=READY`。统计为：10 项资料登记、6 项批准目录文件且哈希全部匹配、48 个目标字段、7 个已有来源候选、41 个缺失或待批准、12 个 gap、0 个开放 P0、5 个目标节点（5 个必需输入闭环完全支持、0 个部分支持、0 个未知/不支持）。这表示第一阶段定义包已完成并可进入内部实现联调；尚未产生 conversion、候选证据、不可变快照、动态 run 或筛查报告，不能宣称端到端试点已经验收通过。
