# 字段合同与覆盖口径

## 1. 字段全集的组成

阶段 1 不把任意单一文件当成完整真相，而是对以下来源求并集并按 `target_path` 去重：

1. `resources/contracts/part1/v1/field_dictionary.json`：当前抽取字段字典，共 280 个字段。
2. `resources/contracts/part1/v1/schemas/qra-input.schema.json`：所有显式叶字段，共 71 个；对象型开放内容不能仅靠 Schema 枚举。
3. 11 个动态节点的当前显式目录要求。
4. AQT 3046、GB/T 34346、人群风险和物理后果适配器的运行时读取项，共补充审阅 60 个字段。

合并后得到 361 个唯一 `field_id` 和 361 个唯一 `target_path`。`contract_sources` 保留每个字段来自哪些合同来源，便于发现 Schema、字段字典和运行时实现之间的漂移。

## 2. 三类数据层

| 数据层 | 定义 | 允许来源 |
|---|---|---|
| `PROJECT_FACT` | 描述当前工程、环境、设备、人口或记录的客观事实 | 10 类合成原始资料 |
| `MODEL_PARAMETER` | 可跨项目复用、需要版本治理的频率、后果、点火、准则和验证夹具参数 | `synthetic-frequency-library-v1`、`synthetic-frequency-correction-v1`、`synthetic-consequence-parameters-v1`、`synthetic-ignition-model-v1`、`synthetic-risk-criteria-v1`、`synthetic-model-validation-fixture-v1` |
| `RUN_ASSUMPTION` | 本次运行的范围、时间窗、模型选择、显式先验或操作假设 | `run-assumption:S00_BASELINE-v1`、项目向导或受控系统生成值 |

分层结果为 260 个项目事实、68 个模型参数、33 个运行假设。项目事实不得从参数包注入，模型参数不得伪装成工程资料，运行假设不得隐藏在代码默认值中。

## 3. 规范矩阵列

文档规定的最小列全部保留：

- `field_id`、`business_name`、`target_path`
- `data_layer`、`source_document`、`source_location_type`
- `source_unit`、`target_unit`
- `criticality`、`extraction_method`、`target_nodes`
- `missing_policy`、`conflict_policy`、`evidence_required`

为支持实现审计，另增加：

- `value_type`、`cardinality`
- `contract_sources`、`node_requirement`、`default_or_prior`
- `mapping_coverage`、`extraction_coverage`、`assembly_coverage`
- `coverage_gap`、`notes`

## 4. 关键性、缺失与冲突

- `BLOCKING`：任一目标节点的必需输入，或当前链路必须显式确认的运行字段。缺失时阻断相关节点或复核门禁。
- `IMPORTANT`：影响结果质量、解释或范围，但可以在明确记录降级后继续。
- `OPTIONAL`：不影响当前节点最低运行合同的补充信息。
- 缺失值不得静默转换为 0。允许的行为只能是阻断节点、进入复核、显式不适用或使用已登记且带版本的先验/默认值。
- 冲突字段必须走显式决策；证据敏感字段不得通过来源优先级直接覆盖冲突。

## 5. 证据和提取方法

- 原始资料字段设置 `evidence_required=true`，证据位置类型按来源登记为页码/边界框、表格单元格、段落或混合位置。
- `deterministic` 用于可按表头、列、结构或规则稳定提取的字段。
- `ocr` 用于扫描页和现场图像中的可定位文字。
- `llm` 只用于受 Schema、证据绑定和复核约束的语义提取。
- `manual` 用于原始资料缺失且业务允许人工补录的明确值。
- `system` 用于版本参数包、运行假设包或可重放的系统派生值。

## 7. 覆盖缺口的含义

以下数量是阶段 1 冻结时的基线：`coverage_gap=NONE` 当时表示映射、抽取 Schema 和复核组装链已能消费该字段，共 143 个；其余 218 个字段已有完整字段合同，但至少一个实施环节尚未支持：

- `DETERMINISTIC_MAPPING_GAP`：现有来源映射没有写入目标路径。
- `EXTRACTION_SCHEMA_GAP`：字段不在当前字段字典中，抽取候选合同会拒绝它。
- `REVIEW_ASSEMBLY_GAP`：现有复核组装器无法创建所需目标对象或实体容器。
- `PARAMETER_PACK_MERGE_NOT_IMPLEMENTED`：字段已有版本参数包归属，但参数包注入/合并链尚未实现。

2026-09-02 起，以 `coverage-gap-closure.json` 为当前状态源；原登记册仅保留历史发现证据。关闭记录区分已实现、仅参考快照和未演练三类，禁止把“有字段合同”或“参考快照中有值”表述成“已有原始证据提取”。

阶段 1 的目标是完整定义并检测这些合同，不提前把阶段 2、阶段 3 的实现缺口误报为已覆盖。

## 8. 自动检测机制

`tools/build_full_chain_stage1_contract.py` 每次从当前字段字典、QRA Schema 和动态节点目录重新计算合同，校验以下不变量：

- 当前 11 个节点全部被导出；新增或删除节点会导致验收失败。
- 字段字典和显式 Schema 字段全部进入矩阵；遗漏会导致验收失败。
- 每个节点必需输入都有来源且为 `BLOCKING`。
- 三类数据层只能使用各自允许的来源。
- 已提交生成物与当前代码计算结果逐字节一致；`--check` 发现漂移后返回非零退出码。

这使后续新增节点、字段或修改来源策略时，必须同步更新合同，而不能静默绕过矩阵。
